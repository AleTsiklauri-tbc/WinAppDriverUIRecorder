# Architecture

WinForms Recorder is a locator inspector and test recorder for .NET Framework WinForms apps automated with WinAppDriver.
This document maps the legacy WinAppDriver UI Recorder to the new design, records decisions,
and keeps the **Findings**: verified facts about what UI Automation and WinAppDriver actually expose.
"Spec n.n" means a section of [SPEC.txt](SPEC.txt), the original specification.

## 1. Constraints that shape the design

- **Local only.** No telemetry, update checks or crash reporters. The only network code allowed is the
  optional WinAppDriver client in `src/Recorder.Core/Verification`. A unit test enforces this (section 6).
- **Privacy.**
  - Password values are never read. Printable keystrokes are never recorded.
  - Customer data is never derived into names or logs. In LMS, window titles carry the open customer's name and ID.
- **Responsiveness.** The UI thread never calls UI Automation. Every UIA call has a timeout. A hung target never freezes the recorder.
- **Fidelity.** UIA3 (COM `UIAutomationClient` via FlaUI), the same API WinAppDriver uses.
- **No admin.** Per-monitor-V2 DPI aware. Ships as a self-contained single-file exe for win-x64 (`./build.ps1 publish`, D-82).

## 3. Runtime design

```text
 UI thread (WPF, MVVM)                         UiaWorker thread (MTA)              Hook thread
 ─────────────────────                         ──────────────────────              ───────────
 Views ◄─bind─ ViewModels ◄── Core services ──► Channel<UiaRequest> ──► UIA3Automation   WH_MOUSE_LL / WH_KEYBOARD_LL
                     ▲          (async, CT)     latest-wins hover        CacheRequest      copy event → Channel → return
                     │                          2 s timeout per call     ElementFromPoint
                     └──────── toasts / banners ◄── GlobalExceptionHandler (log + plain message + "Copy details")
```

- **Hosting.**
  - `Microsoft.Extensions.Hosting` with `DisableDefaults`, so no configuration sources and no log providers are added implicitly.
  - Serilog writes to one local rolling file: `%LOCALAPPDATA%\WinFormsRecorder\logs\recorder-YYYYMMDD.log`, kept for 7 days, 50 MB cap per file.
  - Start and stop are fully async; there is no blocking wait on the UI thread.
  - Every log message has its own EventId (`LogEventIdTests`), in ranges by service: 1–2 unhandled errors, 100s start and stop,
    200s UI Automation (`UiaWorker` 200, `UiaService` 210, `LocatorService` 220), 300s settings, 400s `TargetTracker`, 500 hover,
    600s app services (hotkeys 600, capture 610, locating 620, recording 630, WinAppDriver 632, recording files 640),
    700s the recording session, 900 code profiles, 910 code files, 920 autosave. A new service takes the next free ten.
- **Errors.**
  - `DispatcherUnhandledException`, `TaskScheduler.UnobservedTaskException` and `AppDomain.UnhandledException` are logged.
  - The user sees a plain message. The technical details reach the clipboard only through "Copy details".
- **Data locations** (`AppPaths`):
  - Settings and profiles go to `%APPDATA%\WinFormsRecorder`; logs and autosaves go to `%LOCALAPPDATA%\WinFormsRecorder`.
  - `WINFORMSRECORDER_HOME` redirects everything into one folder. Tests use it, and it doubles as portable mode.
- **Strings.**
  - All user-facing text lives in `Recorder.App/Resources/Strings.resx`.
  - The strongly typed `Strings` class is generated by an MSBuild target before every compile (see D-15).
- **Capture engine (Phase 1).**
  - `UiaService` is the only door to UI Automation. Every call runs on one dedicated MTA thread (`UiaWorker`) and returns a
    `UiaResult` with a status (`Ok`, `NothingThere`, `OwnWindow`, `Busy`, `AccessDenied`, `Gone`, `Cancelled`); nothing throws to the UI.
  - `ElementSnapshotFactory` reads an element and all its ancestors through two `CacheRequest`s (raw view), so a capture is a few
    cross-process calls. Values are read live and never for password fields (`IValueReader` seam, tested with a spy).
  - Hover requests share a latest-wins lane. Every caller gets an answer within the timeout + 0.5 s (D-29); a call stuck for
    4 × the timeout gets its thread replaced (`Restarts`).
- **Target.** `TargetTracker` remembers the target by process name, polls once a second in the recorder's own Windows session, and moves
  between `None`, `Attached`, `Waiting` (not started or closed) and `Elevated`. It is also the `ITargetFilter` that decides ownership (D-24).
- **Pick mode.** `HoverTracker` polls the cursor (25 ms), debounces (40 ms) and publishes deduplicated hover updates; `PickSession`
  installs the low-level mouse hook only while picking and swallows exactly one left click over the target (D-21).
- **Overlay.** `HighlightOverlay` = four click-through layered edge windows plus one label-chip window, positioned in physical pixels (D-19).
- **Locator engine (Phase 2).** Pure Core code, no UI Automation inside:
  - `LocatorSpec` is the AST (steps, predicates, `(…)[n]` result index); `XPathRenderer` renders it for WinAppDriver.
  - `IdRules`, `NameRules` and `ClassNameRules` grade each attribute (High / Medium / Low, or rejected with a reason code).
  - `CandidateGenerator` drafts candidates, `LocatorRefiner` makes a non-unique one unique (control type → anchor → attribute →
    index), and `LocatorEngine` counts matches, scores and ranks them (D-34). `LocatorEvaluator` counts exactly as WinAppDriver does (F-20, F-21).
- **Uniqueness (Phase 2).** `LocatorService` runs on a **second** UIA worker, so a slow window never delays hovering. `TreeFetcher` reads the
  target window's whole raw-view subtree in one cached call (`UiTree`); every candidate is then evaluated locally (F-19, D-33). Hover checks
  reuse that tree for 2 s.
- **Verification (Phase 2).** `WinAppDriverClient` (the only HTTP code, loopback-only by default) and `LocatorVerifier`: one session per
  check, attached to the window, one find per candidate, session deleted (the app keeps running, F-24). Nothing polls (spec 11.2).
- **Naming (Phase 2).** `VariableNamer` suggests camelCase names from the AutomationId, the nearby label (`LabelFinder`) or the Name,
  transliterating Georgian and Russian; `JavaLocatorLine` renders the D-5 getter.
- **Recording (Phase 3).** `RecordingSession` (Core) observes and never acts on the target (F-14):
  - The hooks only copy events. `ClickResolver` looks the element of a press up at once: the hover cache (`HoverTracker.Latest`,
    a resting cursor re-read every 150 ms) if younger than 250 ms and containing the point, else the point itself (D-44).
    Everything else runs on one ordered loop (`SessionLoop`), so nothing is reordered or lost; `HookWatchdog` reinstalls a
    hook Windows removed (D-56).
  - Text is never captured from keys. `WatchFocusAsync` reports focus changes (and where focus is at start) as snapshots;
    `ValueTracker` compares an input's value at focus-in and focus-out, before any click or recorded key, and on pause and
    stop (D-51). Password fields are never read: typing into one becomes a test-data step (D-50).
  - `SpecialKeyHookService` (WH_KEYBOARD_LL) sorts keys by virtual-key code alone (`KeyClassifier`); its header lists the privacy guarantees.
  - `StepBuilder` (pure) turns clicks, values, keys, scrolls and assertions into `StepDraft`s and `StepChange`s (added or replacing an
    earlier step). `StepTargets` decides what a click really targets (combo box, grid, first menu item) from the snapshot alone.
  - The app's `StepRecorder` puts the drafts' elements into the catalog (with locators checked while hovering, D-47) and the steps
    into `StepList`; `RecordingCoordinator` owns the session, the shortcuts (D-48) and the mini-bar; `AssertController` runs Assert mode.
  - Recordings are saved and opened by `RecordingStore` as schema-versioned `*.wfrec.json` (D-52).
- **Code generation (Phase 4).** Pure Core code in `CodeGen/`; templates are documented in [TEMPLATES.md](TEMPLATES.md).
  - `ProfileLoader` reads the embedded profiles and the user's folders (D-60). `CodeGenerator` turns the catalog and the steps into
    page, Steps and test classes: `CodeModelBuilder` builds the template model (`PageCode`, `ActionCode`, `TestCode`…), `ActionFactory`
    names a Steps method per action kind and element and renders `action.<Kind>.sbn`, and `TemplateRenderer` runs Scriban with strict
    variables (D-69). Names come from `CodeNames` and `KeyCode`; nothing is derived from a window title (D-61).
  - `CodeMerger` merges one generated class into an existing file with `ClassReader` (comments and literals masked, braces counted,
    declarations matched with the profile's patterns) and gives up with a `MergeProblem` code rather than guess (D-66).
  - In the app, `CodeProfiles` holds the active profile, reloads the profiles folder on change and reports a broken profile in a
    banner; `RecordingChangeWatcher` fires 150 ms after the catalog, steps, names, chosen locators or recording file change;
    `CodeViewModel` then regenerates and shows a template error in place of the code; `CodeFiles` saves, exports and merges (the
    preview is `MergePreviewWindow`, DiffPlex). The editor's `ReadableHighlightingColorizer` keeps syntax colours at 4.5:1 contrast
    in either theme. The locator card's line is the profile's `snippet.sbn` (D-32).
- **UX (Phase 5).**
  - Settings apply as soon as they change. `SettingsStore.Changed` (raised on the thread that made the change) is followed by
    `ThemeService` (theme), `MainWindowLayout` (code pane), `AppHost.FollowLogSetting` (log level) and the code pane (profile).
    `SettingsDialog` opens the Settings window (`SettingsWindow`, with a new `SettingsViewModel` each time) at a section (D-71).
  - `Shortcuts` owns the four global shortcuts. It checks new keys (`ShortcutRules` in Core, then a `HotkeyService.IsFree`
    probe), saves them, registers them again where they are in use, and fills the shortcut placeholders in UI texts (D-72).
    The cheat sheet is an overlay in `MainWindow` over `CheatSheetViewModel` (D-73).
  - `AutosaveService` (Core) writes one file per session and finds what earlier sessions left. The app's `Autosaver` writes
    2 s after a change (its own `RecordingChangeWatcher`), clears after `RecordingFiles.SavedOrOpened` and at a clean exit,
    and offers a leftover in a banner (D-74). `RecordingFiles` also opens recent files and restores (D-75).
  - `MainWindowLayout` restores and saves the window and its splits and moves the code pane (D-76). While recording, toasts
    show in the mini-bar window (D-78) and the code waits until the main window shows again (D-81).

## 4. Legacy → new mapping

The legacy recorder is .NET Framework 4.6.1 WPF plus a native C++ DLL (`UIXPathLib`). Line references point into `legacy/UIRecorder`.

| Legacy part | What it did | Why it fails | New home |
|---|---|---|---|
| `UIRecorder/App.xaml.cs` | Startup; ApplicationInsights (`User.Id = Environment.UserName`); `SetProcessDPIAware` | Telemetry; system-DPI only | `App.xaml.cs` + `Hosting/AppHost.cs`; PerMonitorV2 `app.manifest`; **telemetry dropped** |
| `MainWindow.xaml.cs` | UI controller; statics (`s_mainWin`, `s_windowHandle`); `PostMessage` ids 3001–3006 (WM_USER range); `List<>` bound to `ItemsSource` and mutated from the recorder thread | Races; blocking highlight (up to 30 s); dead menu item | MVVM views + view models; state in Core models; cross-thread work through channels and async |
| `MouseKeyboardEventHandler.cs` | Recorder thread; 125 ms hover timer; 750 ms double-click; 15 px threshold; keystroke buffer | Click bound to the *last hovered* path; tree building inside the hook; keylogging | `Recording/` (Phase 3): mouse hook copies and returns; hover cache < 250 ms or re-resolve at the click point; system double-click time; 8 px threshold |
| `MouseKeyboardHook.cs` | Installs `WH_MOUSE_LL`/`WH_KEYBOARD_LL` | `HHOOK` truncated to `uint`; `CallNextHookEx` called twice; logical/physical coordinate mix | `MouseHookService`; `SpecialKeyHookService` (virtual-key only; printable keys dropped in the callback) |
| `GenerateXPath.cs` | Absolute XPath from parsed native strings; VK → text tables | Absolute paths; `WindowsForms10.*` collapsed; over-broad digit regex; several bugs | `Locators/`: `LocatorSpec` AST, rules, uniqueness, refinement, rendering (Phase 2). **VK tables dropped** |
| `RecordedUiTask.cs` | Task model plus C# code generation (`FindElementByAbsoluteXPath`, `Thread.Sleep(100)`, `Console.WriteLine`) | Wrong language; no page objects | `Model/RecordedStep` + `CodeGen/` with Scriban profiles (Phase 4) |
| `UiTreeNode.cs`, `XmlNodePathRecorder.cs` | Parses `/Tag[attr="v"]…` strings back into trees | String parsing; statics | `ElementSnapshot` + `AncestorInfo` built directly from cached UIA properties |
| `WindowEditNodeAttribute.xaml(.cs)` | Hand-edit XPath node attributes | Manual and error-prone | Inspector "Other locators" plus "Advanced" (Phase 2) |
| `UIXPathLib/UiTreeWalk.cpp` | `ElementFromPoint`; RawViewWalker walk to the desktop; highlight drawn on the desktop DC with a 500 ms timer | Native DLL; blocking; screen artifacts | `Automation/` with FlaUI + `UiaWorker` + `CacheRequest` (Phase 1); layered transparent overlay window |
| `UIRecorderTemplate/` | C# MSTest skeleton | Wrong stack | **Dropped**; profiles generate Java for the target framework |
| `ApplicationInsights.config`, AI packages | Telemetry | Unacceptable in a bank | **Dropped** |

**Ported as ideas, rewritten.** Each is credited in `THIRD_PARTY_NOTICES.md`.

- The GUID regex `[0-9a-fA-F]{8}-…-[0-9a-fA-F]{12}`.
- The dynamic-digit-suffix → `starts-with` heuristic, narrowed to long or separated suffixes. The legacy `^([^\d]*)[_\.\-\d]+$` also matches designer names such as `textBox12`.
- `ElementFromPoint` → ancestor chain.
- Excluding the recorder's own windows from capture. The legacy auto-paused while the cursor was over its window; the new code filters by process.

**Dropped.**

- The native DLL.
- Telemetry.
- Keystroke decoding tables.
- Static state and `PostMessage` plumbing.
- The C# code generator.
- Absolute XPath as a default. It is still available on demand in "Advanced".

## 5. Decisions

| Id | Decision | Why |
|---|---|---|
| D-1 | Repo at `%USERPROFILE%\source\repos\WinFormsRecorder` | Accepted at analysis |
| D-2 | .NET SDK 10.0.403 installed per user (`%LOCALAPPDATA%\Microsoft\dotnet`, SHA-512 verified), pinned in `global.json`; no PATH change | No admin; machine has only SDK 9 |
| D-3 | NuGet only via Nexus `nuget-group` | api.nuget.org is blocked |
| D-4 | Java output is Page + Steps + Test classes | Matches the three layers of LMSAutomationDemo |
| D-5 | Locators are emitted as `public WebElement getX(){return winDriver.findElementBy…("…");}` | java-client 7.6.0 (Selenium 3); `AppiumBy` does not exist there |
| D-6 | Edit naming keeps the ID's own suffix (`amountEditBox` → `getAmountEditBox`), otherwise `Input` | Codebase uses EditBox 17×, Input 6× |
| D-7 | WebView2 content in scope for inspect, capture and locators; no web-specific recording | LMS insurance flows are WebView2 forms (F-12) |
| D-8 | Pages are keyed by the nearest Form (MDI child or dialog), not only by top-level windows | LMS is MDI (F-15) |
| D-9 | Passwords and masked values: the Steps method takes a parameter; the test passes `ConfigReader.getProperty("<KEY>")` | No secrets in code |
| D-10 | Java compile check uses the real java-client 7.6.0 / Selenium 3.141.59 jars from `~/.m2`, plus stubs of the base classes | Stronger than stubs alone |
| D-11 | `docs/target-style/` holds ClientSearchPage, ClientSearchSteps and ChangeOfTermsTest (sanitized) | Accepted at analysis |
| D-12 | Grid row indexes are 0-based | Matches UIA names (F-6) and `GridSteps.clickCell` |
| D-13 | Tests use xUnit v3 (`xunit.v3.mtp-off`) + VSTest adapter + Shouldly | The default `xunit.v3` package pulls in `Microsoft.Testing.Extensions.Telemetry` → `Microsoft.ApplicationInsights` |
| D-14 | Built-in WPF Fluent theme (`ThemeMode="System"`); no WPF-UI yet | Nothing needed beyond built-in controls in Phase 0; WPF0001 was not raised on .NET 10 |
| D-15 | `Strings.resx` → generated `Strings` class via a `GenerateStringsClass` target (`BeforeTargets="CoreCompile"`) | WPF's temporary XAML compile project skips `CoreResGen`, so standard strongly typed resources fail to compile |
| D-16 | Toolbar buttons for later phases are present but disabled | Layout, AutomationIds and tooltips are fixed early; each phase enables its own |
| D-17 | The first-run pulse uses a 1.2 s fade cycle, static when Windows animations are off | A pulse limited to the ≤150 ms rule would not be "gentle"; transitions elsewhere stay ≤150 ms |
| D-18 | Error toasts stay 8 s (info toasts 2.5 s) and have Dismiss | Time to press "Copy details" |
| D-19 | **Deviation from spec 8.4:** the overlay is raw Win32 layered windows (same extended styles: `WS_EX_LAYERED \| WS_EX_TRANSPARENT \| WS_EX_NOACTIVATE \| WS_EX_TOOLWINDOW \| WS_EX_TOPMOST`), not a WPF `Window`. Four edge windows + one chip window; pixels come from `UpdateLayeredWindow`; the chip is rendered by WPF into a bitmap at the monitor's DPI | A WPF window is laid out in DIPs and WPF rescales/moves it when it crosses monitors with different DPI; raw windows are placed in exact physical pixels on any monitor, and four thin windows leave the element itself uncovered |
| D-20 | Phase 1 highlight styles are Neutral (purple) and Captured (blue, dashed, check-mark glyph). Green/amber/red by locator quality arrive with the locator engine in Phase 2 | Quality is unknown before Phase 2 |
| D-21 | The recorder never clicks or invokes anything in the target (F-14). Pick mode captures with a `WH_MOUSE_LL` hook that swallows one left-down over the target and its matching left-up | Spec 8.5; a UIA click could hang the recorder |
| D-22 | The capture shortcut with no app chosen targets the app under the cursor ("Now automating …") | Saves the first step for new users |
| D-23 | The shortcut is changed in `settings.json` (`captureHotkey`) until the Settings UI (Phase 5). A taken shortcut shows a warning banner | Spec 8.5 / Phase 5 |
| D-24 | An element belongs to the target when its process **or the process of its top-level window** is the target's | WebView2 content is served by `msedgewebview2.exe` (F-12) |
| D-25 | A resting cursor is looked up again 500 ms after the last lookup finished, never while one is running. A "busy" answer is shown even if the cursor moved on while waiting for it | A busy target recovers, or a dialog opens, without the mouse moving. "Busy" describes the target, not the point: showing it at once means "not responding" appears after one timeout, not two |
| D-26 | The target selector's entries are buttons (click, Enter, Space and UIA Invoke choose); the Pick toggle is bound two-way so the UIA Toggle pattern works like a click | Spec 11.8: the recorder itself is automatable |
| D-27 | All disposals are idempotent, and closing the main window always ends the process (`finally { Shutdown(); }`) | The DI container disposes `TargetTracker` twice (as itself and as `ITargetFilter`); the second dispose threw and left a windowless process holding the shortcut (found and fixed in Phase 1) |
| D-28 | Element labels in Phase 1 are `ControlType · id` (or the quoted Name, or just the type); variable names and the strategy badge arrive in Phases 2 and 4 | Naming rules are Phase 4 |
| D-29 | Every `UiaService` call answers within the UIA timeout + 0.5 s (2.5 s by default). A call still running is reported Busy; the worker finishes it in the background and its result is dropped. The worker thread is replaced only after 4 × the timeout | Spec 8.1 ("guard every UIA call with a timeout"); UIA's own timeouts add up per step (F-16) |
| D-30 | Locator warnings and explanations are codes (`LocatorNote`, `LocatorExplanation`) in Core; the sentences live in `Strings.resx` | Spec 11.10: all user text in resources; Core stays UI-free |
| D-31 | Variable names and the nearby-label heuristic were pulled forward into Phase 2 (`Naming/`) | The 13.3 test needs `dzebnaButton`, and the Java line needs a getter name |
| D-32 | "Copy Java line" (Ctrl+C) uses the D-5 getter with the variable name, e.g. `public WebElement getAmountInput(){return winDriver.findElementByAccessibilityId("txtAmount");}` | Pastes straight into a page class today; Phase 4 profiles replace it |
| D-33 | Uniqueness is decided on one cached subtree read, evaluated locally; if the target does not answer within 1.5 s the card says "Not checked" instead of guessing | Spec 7.4 budget (< 300 ms): measured p95 167 ms (F-19) |
| D-34 | Scores: AutomationId (whole or `starts-with` prefix) 100, Name 70, ClassName 50, anchored XPath 45, indexed XPath 20, absolute XPath 0; +50 unique, −80 not unique, −10 per warning, −30 for Low stability. The best locator is the highest-scoring unique one; a position-based fallback is always offered | A stable id prefix is as good as an id; positions only as a last resort |
| D-35 | Id rules, in order: reject empty, title-bar (F-22), window handles (F-3), the process id, GUIDs; all-digit → Low; designer default (`textBox12`: camelCase type + 1–3 digits) → High with a note; ≥ 4 trailing digits → Low with `starts-with`; web ids ending in separator + digits (`datepicker-3`) → Low | The legacy `^([^\d]*)[_\.\-\d]+$` rejected designer names; LMS uses designer names (F-1) |
| D-36 | Indexed XPaths use the `(//…)[n]` form, never `//Tag[n]` | They mean different things in WinAppDriver (F-20) |
| D-37 | The WinAppDriver address is edited in the Verify panel and saved to `settings.json` until the Settings UI (Phase 5). Default `http://127.0.0.1:4723` (spec); only loopback unless `allowRemoteWinAppDriver` | LMSAutomationDemo uses port 4727, so its users change it once |
| D-38 | Elements in an unowned pop-up (a ComboBox drop-down list) get Desktop scope: the card says "1 match ✓" (not "in window") and Verify uses a Root session | A window session cannot see them (F-23) |
| D-39 | The Elements list shows the variable name, the strategy badge and a tick; its accessible name is the variable name. Rename in the Inspector header (F2 from the list); leaving the box unchanged does not pin the name | Spec 11.2; names are what the user pastes into Java |
| D-40 | The hover outline appears at once in neutral purple and takes its quality colour when the hover check answers | Spec 8.4 colours without slowing the 100 ms highlight |
| D-41 | When the environment variable `WINFORMSRECORDER_NUGET_SOURCE` is set, `Directory.Build.props` makes it the only restore source (`RestoreSources`), replacing the Nexus feed in `NuGet.config` | The repo is continued on PCs outside the bank's network; nothing changes on it, and other repos on that PC are unaffected |
| D-42 | When the element at a point is a MenuBar, Menu or ToolBar, capture uses its child whose bounds contain the point (up to 3 levels). Hover, Pick, the capture shortcut and recording all go through it; the Phase 1 hover test's independent probe applies the same rule | Hit tests stop at the strip (F-25): menu items and image-only toolbar buttons could not be captured or recorded at all |
| D-43 | **Deviation from spec 9.5:** SwitchWindow is inserted only when a step's element lies in another top-level UIA window than the steps before (and back). Owned dialogs, message boxes, menus and context menus are nested under the main window (F-7, F-23, F-28) and get none | A main-window WinAppDriver session already finds them; the acceptance flow (message box) has no switch. A separate, unowned form still gets one |
| D-44 | A press uses the hover snapshot when it is younger than 250 ms and contains the point; while recording a resting cursor is looked up again every 150 ms so that it stays younger. Otherwise the point is looked up at once; a busy target is asked again every 500 ms for up to 10 s and the click is kept (warning "Element changed" when it was looked up late, an unidentified click when it never answered). Press and release within 8 px are a click on the press's element; farther is a drag, ignored | Spec 9.2; the 500 ms refresh of Pick mode would make the cache older than 250 ms; no click may be lost (F-16) |
| D-45 | A click (or double-click) on an input followed by a value step on that input is replaced by the value step; consecutive value steps on one input collapse into the last | The acceptance flow is "type amount → type password", with no clicks; WinAppDriver's sendKeys focuses the input itself |
| D-46 | Inside an input, editing keys (arrows, Delete, Ctrl+A/C/V/X/Y/Z) and Enter in a combo box are not recorded: the new value is. Special keys are recorded only while the target is in front, never the recorder's own shortcuts, and in a password field only Enter and Tab (D-59) | Recording both the keys and the value would replay the edit twice |
| D-47 | The locators of an element under the resting cursor are checked while recording (`LocatorPrefetcher`, hover lane) and used when a step's element enters the catalog within 30 s; otherwise they are checked after the step, as for a capture | A message box's OK button is gone once clicked, so a check after the click finds nothing |
| D-48 | F9 is registered while the recorder runs; F10 and Ctrl+Shift+A only while recording; Esc only in Pick and Assert mode. All three are set in `settings.json` (`recordHotkey`, `pauseHotkey`, `assertHotkey`) until the Settings UI | Global shortcuts take the key from every other app: F10 is Step Over in Visual Studio |
| D-49 | Recorded steps are not in the undo history; every edit is (delete, duplicate, move, edit, rename, choice of locator). Del removes a recorded step, undoably, with an Undo toast | Undo right after recording should not silently drop recorded steps |
| D-50 | With the keyboard hook, a key that types (or Delete) in a password field sets a flag carrying no key; at focus-out that becomes one SetText with TestDataKey = the field's variable name. Without the hook (refused, or `recordSpecialKeys` off), one visit to a password field counts as typing, once | Spec 9.3 says to emit the test-data step but not when; the value can never be compared because it is never read |
| D-51 | The value before typing comes from the snapshot of the click that focused the input (read before the click), else from the focus event's snapshot. VK_PACKET and IME keys count as typing | Typing can start before the focus event is handled; Unicode input arrives as VK_PACKET (F-30) |
| D-52 | `*.wfrec.json` schema 1 holds the target process name, pages, elements (identity, variable name, chosen locator, all candidates with their AST) and steps; never element values, window titles, ancestors or runtime ids. ## 6. Guard rails in tests

- `NoNetworkingTests` fails if any of these appear outside `src/Recorder.Core/Verification`, or if a telemetry, crash-reporting or updater package appears in any restored dependency graph (`project.assets.json`, transitive included):
  - source files under `src/` contain `HttpClient`, `ApplicationInsights`, `Telemetry`, `WebRequest`, `WebClient` or `System.Net.Sockets`;
  - a `<PackageReference>` names such a package.
- `FirstRunTests.Every_button_has_an_AutomationId_and_an_accessible_name` keeps the recorder automatable (spec 11.8), and
  `AccessibilityTests` extends it to every interactive control and list in the main window (both tabs), in every Settings section
  and in the cheat sheet, without input (D-80).
- `LogEventIdTests` fails when two log messages share an EventId.
- `PublishProfileTests` keeps the publish profile self-contained, single-file and win-x64, with every PDB embedded (D-82), and
  `./build.ps1 publish` fails when anything but the exe lands in the publish folder. `./build.ps1 test -Published` runs the
  integration tests against the published exe (`WINFORMSRECORDER_RECORDER_EXE`).
- End-to-end tests drive the real recorder and the real SampleApp with real input (`SendInput`, `SetCursorPos`). They put the cursor back
  and carry `[Trait("Category", "Input")]`; skip them while you work with `./build.ps1 test -NoInput`.
- `CaptureEndToEndTests.Hovering_any_control_…` hovers every distinct element of the SampleApp (68 on this machine) and checks the
  four edge windows against what an independent UIA client reports under the same point.
- `./build.ps1 test -Monitor n` (`WINFORMSRECORDER_TEST_MONITOR`) puts the SampleApp of the end-to-end tests on monitor n (1 is the main
  display, the others follow from left to right): spec 14's two-monitor acceptance is one run per monitor. `RecordingEndToEndTests` also
  checks that the mini-bar is at the top center of the app's monitor, and `AssertAndEditEndToEndTests` that the assertion picker opens
  next to the click, on its monitor. `WindowPlacementTests` close the recorder on each of two monitors, normal and maximized, and check
  that it opens there again at the same size (D-76), without input; they are skipped with one monitor.
- `LocatorTests` holds the spec 13.3 cases (every control unique, the two Save buttons, `ძებნა`, dialogs, timings).
- `WinAppDriverComparisonTests` (`[Trait("Requires", "WinAppDriver")]`) compare the tree shape in five window states and the match count
  of **every** generated candidate with a real WinAppDriver. They are skipped when nothing answers at `WINFORMSRECORDER_WINAPPDRIVER_URL`
  (default `http://127.0.0.1:4723`; `./build.ps1 test -WinAppDriverUrl http://127.0.0.1:4727`). The full run takes about 10 minutes.

  `RecordingSessionTests` drive the real session loop with fake hooks and a fake UIA service, and check that a password field's value is
  never read (`FakeUia.StateReads`).
